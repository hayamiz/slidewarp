# 設計: ダークテーマ・スライドの sub-slide 誤検出対策 ＋ 評価基盤の信頼化

- 日付: 2026-08-08
- 対象: Rust 本体（`src/detect.rs` / `src/report.rs`）
- 発端: `input-samples2/`（FMS 2026 出張・402枚）と途中までの評価 JSON
  (`input-samples2/warped/slidewarp-eval.json`) のレビュー

## 背景と問題発見

新データ 402 枚に対し、現行チェックイン済み Rust 検出器（`target/release/slidewarp`,
2026-08-07 ビルド）が出力した `warped/` を精査した。出力の confidence は再実行と完全一致し、
`warped/` は**現行アルゴリズムの出力で確定**。評価は 138/402 まで（途中）。

分析で 2 つの事実が判明した。

### 発見①: crop=1「画像が出ていない」クラスタは評価UIの表示欠落アーティファクト
crop=1「画像が出ていない/処理後のファイルがない」が 27 件あるが、**出力ファイルは実在し、
うち約 20 件は完璧〜良好な切り出し**だった（例: 09.15.43, 12.12.40, 11.32.14, 12.18.42）。
レビューUI 上でサムネイルが表示されず、評価者が 1/1 のプレースホルダを記入したもので、
**検出失敗ではない**。このクラスタを額面通り「不良」と数えると誤診する。

### 発見②: 真の検出不良は 2 系統に集中
現行 Rust 検出器で 100% 再現する真の不良は主に次の 2 つ（少数の天井混入・左右クリップ・歪みを除く）:
1. **sub-slide（内部の一部だけ切り出す）約 24 件** — 最大かつ最難。**ダークテーマ**
   （暗背景に明るい 3D 図/製品写真/グラフ/枠付き画像）で多発。旧 24 枚セットにほぼ無かった新条件。
2. **上端クリップ 約 16 件** — 明るいスライドのタイトル帯が上で切れる。→ **今回スコープ外**。

本設計は、ユーザ選定により **① 評価基盤の信頼化** と **② ダークテーマ sub-slide 対策** の
2 本柱に絞る。上端クリップ・天井混入等は別ラウンドとする。

## Pillar ①: 評価基盤の信頼化

### 目的
`--report` の出力を、402 枚規模でも全数が確実に表示される信頼できる評価基盤にし、
Pillar ② の改善を「全数・回帰ゼロ」で定量判断できるベースラインを確立する。

### 根本原因（仮説、実装前に再現で確定）
`report.html` は out_dir 内の全画像を**フル解像度でインライン**（`loading="lazy"`,
`src/report.rs:158,168`）し、画像パスに**スペースを含む**。402 枚（合計約 240MB）を
1 ページに並べるため、ブラウザで一部が描画されず（lazy-load 失速／メモリ）、
または一部パスの解決に失敗し「画像が出ていない」状態になる。

### 変更方針（`src/report.rs`）
1. **サムネイルの data URI 埋め込み**: レポートに表示する画像は、各画像を長辺 ~480px へ
   縮小した JPEG を **base64 data URI** として HTML に埋め込む。402 枚でも合計数 MB に収まり、
   全数が確実に描画される。**自己完結 HTML** になり配布・別マシン評価にも強くなる。
2. **クリック拡大はフル解像度をパス参照**、その参照は **URL エンコード**（スペース→`%20`）する。
3. これにより表示欠落の 2 大要因（大量フル解像度の失速・スペース）を同時に解消する。

### インタフェース／境界
- 変更は `report.rs` に閉じる。呼び出し側（`main.rs`）が渡す `Item`（`src`/`out` のパス）は
  そのまま利用し、report 側で「サムネイル生成（縮小 JPEG → base64）」と「拡大用 URL エンコード」を行う。
- サムネイル生成には既存依存の `image` crate を用いる（新規依存なし）。生成は元画像・出力画像の
  両方に対して行う。
- 出力アスペクトや検出結果には一切影響しない（表示層のみの変更）。

### スコープ外
- Python 版 `report.py` の同期（任意・別途）。評価は Rust `--report` に統一する。

### 検証（Pillar ①）
- 402 枚で report を再生成し、**全 402 枚のサムネイルが表示される**ことを目視確認
  （表示欠落ゼロを明示チェック）。
- 修正前に「画像が出ていない」だった代表数枚が、修正後レポートで正しく表示されることを確認。
- 全 402 枚（＋旧 24 枚）を人手評価し直し、**信頼ベースライン**（crop/look 分布）を確定・記録する。

## Pillar ②: ダークテーマ・スライドの sub-slide 対策（A案）

### 根本原因（構造的）
現行検出器は全体が **「暗い会場の中の明るいスライド」** という前提で組まれている。
ダークテーマのスライドはこの前提を破り、候補生成〜採点まで一貫して誤る。

| 段階 | 明るいスライド前提 | ダーク背景スライドで起きること |
|---|---|---|
| `brightness_mask`→`bright_bbox` | スライド全体を明部として捕捉 | **明部＝内部の明るい要素だけ**。スライド全体は暗く拾わない |
| hough ROI (bbox×1.18) | 外周が ROI に入る | ROI が内部要素に限定され**真の外周線が視野外** |
| contour（mask 由来） | 最大輪郭＝スライド全体 | 最大輪郭＝内部要素 |
| `fill`(0.20) | スライド quad が明部で埋まり高得点 | 真の quad は暗く低 fill、内部要素 quad が高 fill＝**逆転** |
| `contrast`(0.12) | スライド(明) vs 会場(暗) で加点 | 内部要素(明) vs スライド背景(暗) が加点＝**内部要素に加点** |
| `cut`(0.20)＝sub-slide 防御 | 明部を素通しで横切る辺を減点 | 内部要素の**外側は暗い**スライド背景 → cut 発火せず**防御が無効化** |
| `edge`(0.25) | 内側明・外側暗の枠を加点 | 内部要素も内側明・外側暗 → **偽枠に満点** |

単なる重み調整では直らない。**真の全スライド quad がそもそも候補生成されず**、
生成できても fill/contrast/edge が内部要素を選ぶ。生成・採点の両方に手を入れる必要がある。

核心の洞察: 「明部＝スライド」前提を捨て、**プロジェクタ投影領域**としてスライドを分離する。
ダークテーマでも投影面は真っ黒にならず、暗幕/室内の“ほぼ黒”に対して一様な“暗グレー”として浮く。
低しきい値の「非黒（投影領域）」マスクで全スライドを捕捉できる。

### 設計（A案: デュアルマスク生成 ＋ theme-aware スコアリング、条件発火）

すべて**加算・条件発火**とし、明るいスライドの既存経路は無改変に保つ
（プロジェクトの実績あるパターン: 上下辺リファインの後処理化・人物マスクの生成のみ適用）。

1. **投影領域マスクの追加**（`src/detect.rs`）
   - 既存 `brightness_mask` に加え、**低しきい値の投影領域マスク**を生成する。
     暗幕/室内の準黒レベルより上（暗グレー以上）を前景化し、モルフォロジで整える。
     しきい値は「準黒（drape/室内）」と「暗グレー（投影面）」を分けるよう決める
     （実装時に大津の下側モードや低パーセンタイル等の候補から選定・全数評価で確定）。
   - このマスクから全スライドの bbox（`screen_bbox`）を得る。

2. **デュアル候補生成**（`src/detect.rs`）
   - contour と hough を、既存の明部由来に加えて**投影領域マスク／`screen_bbox` でも走らせ**、
     生成された全スライド quad を候補プールへ**マージ**（既存候補は残す）。
   - hough の ROI 限定は `screen_bbox`（×1.18）でも実行し、真の外周線を視野に入れる。

3. **theme-aware スコアリング**（`src/detect.rs` `score_quad` / `edge_profile`）
   - **ダークテーマ判定**を設ける（例: 明部マスク面積比が小さい／投影領域内の平均明度が低い等の指標。
     指標と閾値は実装時に選定し全数評価で確定）。判定が真のときのみ以下を適用する。
   - **fill の基準マスク切替**: ダーク時は `fill` を明部 `fill_holes` 版でなく**投影領域マスク版**で
     評価し、暗く一様なスライド内部が不当に低 fill にならないようにする。
   - **cut 防御の拡張**: 「内部要素の外側がスライド背景（暗）と地続き」パターンを sub-slide として
     捉えられるよう、cut の“外側明”条件をダーク時に緩め、内部小矩形を減点できるようにする。

### インタフェース／境界
- 変更は `src/detect.rs` に閉じる（前処理・候補生成・採点）。`warp.rs`/`geometry.rs`/`main.rs`
  への変更は不要。
- 明るいスライド（旧 24 枚および今回の明るいスライド群）は、ダーク判定が偽なので**現行と同一挙動**。
- 追加マスク・追加候補・theme 判定は独立関数として実装し、単体で挙動を説明・検証できる粒度に保つ。

### リスクと緩和
- **回帰リスク**: 追加候補が明るいスライドで悪さをする可能性 → 追加候補もスコアで競合するのみで、
  ダーク判定が偽なら採点変更は不発。旧 24 枚での回帰ゼロを採用条件とする。
- **ダーク判定の誤判定**: 閾値は全数評価で調整し、境界例（青被り 08.45.45 等）を回帰確認に含める。

### 検証（Pillar ②）
- Pillar ① で確立した信頼ベースラインに対し、`eval-output/` を**フレッシュ再生成**して全数比較。
- **回帰ゼロ**（旧 24 枚＋今回の良好ケースが悪化しない）を採用の必須条件とする。
- ダーク sub-slide 群（11.46.51/12.03.08/12.03.39/12.03.58/12.05.41/11.40.55 ほか）で
  full-slide quad が選ばれることを確認。

## 全体の作業順序

1. Pillar ① を実装 → 402 枚レポート再生成 → 全数人手評価で信頼ベースライン確定。
2. Pillar ② を実装（マスク追加 → デュアル生成 → theme-aware 採点）。
3. `eval-output/` フレッシュ再生成 → ベースライン比較 → 回帰ゼロ確認 → 採否判断。

Pillar ① を先に完了させる理由: 信頼できる定量ベースラインが無いと Pillar ② の
効果・回帰を正しく判定できないため（CLAUDE.md「全数・回帰ゼロ確認後に採用」方針）。
